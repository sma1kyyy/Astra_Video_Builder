# Архитектура системы

## Общее описание

Данный проект представляет собой инструмент для автоматизированной сборки демонстрационных и обучающих видеороликов на основе формализованного сценария. Основная идея заключается в разделении **логики описания процесса** и **логики его визуализации**, что позволяет получить воспроизводимый, контролируемый и масштабируемый пайплайн генерации видео.

Проект ориентирован на создание обучающих материалов (tutorials, walkthrough, onboarding-видео), где важно не просто получить видеоряд, а корректно и последовательно отразить процесс выполнения действий.

---

## Ключевой принцип

Центральным элементом системы является **сценарий** (YAML / JSON), который описывает:

* последовательность шагов;
* визуальные элементы;
* текстовые пояснения;
* временные характеристики.

Видео не генерируется напрямую из произвольного текста. Сначала формируется сценарий, который может быть проверен и отредактирован человеком, и только после этого используется для сборки видео.

---

## Архитектурный подход

Архитектура проекта построена вокруг следующих принципов:

* детерминированность результата;
* прозрачность исполнения;
* минимизация «чёрных ящиков»;
* возможность ручного контроля на каждом этапе.

Система логически делится на три уровня:

```
Текстовое описание / документация
            ↓
     Формализованный сценарий
            ↓
      Генератор видео
```

---

## Сценарий (Script Layer)

Сценарий — это декларативное описание будущего видео. Он не содержит информации о том, *как* выполнять действия, а только *что* и *в какой последовательности* должно быть показано.

Типовое содержимое сценария:

* сцены и акты;
* фоновые изображения или кадры;
* текстовые блоки (заголовки, пояснения);
* позиции элементов;
* длительность отображения;
* параметры анимации.

Сценарий является:

* человекочитаемым;
* версионируемым;
* пригодным для ручного редактирования;
* независимым от конкретного режима рендеринга.

---

## Режимы генерации видео

Генератор видео поддерживает несколько режимов работы. Все режимы реализованы в рамках **одного сервиса** и отличаются только путём выполнения.

### Screenshot Mode

Базовый и приоритетный режим на текущем этапе проекта.

Характеристики:

* видеоряд собирается из заранее подготовленных скриншотов или изображений;
* сценарий определяет порядок, длительность и наложение элементов;
* режим прост в отладке и полностью воспроизводим.

Screenshot Mode используется как минимально достаточный и стабильный фундамент для всей системы.

### Live Recording Mode

Режим автоматической записи действий в интерфейсе с использованием инструментов браузерной автоматизации (например, Selenium / Playwright).

Важно:

* данный режим **не требует использования LLM**;
* действия выполняются строго по сценарию;
* режим является расширением генератора, а не отдельным сервисом.

---

## Использование LLM

Модели машинного обучения (LLM) **не участвуют** в выполнении действий, генерации скриншотов или управлении интерфейсами.

Единственная допустимая роль LLM в рамках проекта:

* генерация сценария (YAML / JSON) на основе текстового описания, документации или инструкций.

LLM:

* не имеет доступов;
* не выполняет клики;
* не взаимодействует с браузером;
* не участвует в рендеринге видео.

Таким образом, LLM выступает исключительно как вспомогательный инструмент подготовки сценария, а не как исполнитель.

---

## Асинхронность и исполнение

Генерация видео является ресурсоёмкой операцией, поэтому выполнение организовано асинхронно.

Используемый подход:

* единый сервис генерации;
* очередь задач;
* брокер сообщений (Redis);
* исполнитель задач (Celery).

Такой подход позволяет:

* масштабировать выполнение;
* контролировать состояние задач;
* избегать усложнения архитектуры микросервисами без необходимости.

Помимо CLI и Celery-очереди, в репо есть **HTTP-обёртка** в `web/` (FastAPI + статический фронт). Она:

* принимает payload конструктора, валидирует его pydantic-моделями (`web/backend/app/schemas.py`) и собирает YAML того же формата, что читает `core/parser.py`;
* кладёт каждое задание рендера screenshot mode в Celery (`core.queue.tasks.render_video_task`) поверх Redis — параллельность регулируется флагом `--concurrency` celery-воркера, web-процесс остаётся отзывчивым;
* хранит маппинг `task_id → output_dir` в простом on-disk реестре (`web/backend/app/jobs.py::CeleryJobRegistry`), чтобы UI знал, откуда отдавать готовые файлы;
* раздаёт результат и хвост лога через REST.

Web-сервис не дублирует Celery — он делит с CLI ту же очередь и таски, добавляя поверх неё конструктор сценариев, загрузку ассетов и скачивание результата. Live Recording через web запускать нельзя: запись экрана требует физического display server, недоступного в headless-контейнере.

---

## Логирование и диагностика

На текущем этапе проекта используется базовая система логирования:

* статус выполнения задач;
* ошибки;
* время выполнения этапов.

Метрики, системы мониторинга и визуализации (Prometheus, Grafana) намеренно не используются, так как не являются обоснованными для масштаба проекта и не дают практической пользы на данном этапе.

---

## Причины выбранной архитектуры

Выбранный подход позволяет:

* избежать избыточной сложности;
* сохранить контроль над результатом;
* обеспечить воспроизводимость;
* упростить тестирование и отладку;
* поэтапно расширять функциональность без переработки основы.

Архитектура ориентирована не на демонстрацию технологий, а на решение прикладной задачи — генерации корректных и понятных обучающих видеоматериалов.

---

## Статус проекта

Текущий фокус разработки:

* развитие Screenshot Mode;
* формализация структуры сценариев;
* улучшение визуальных элементов (текст, подложки, фокус);
* повышение стабильности пайплайна.

Расширение функциональности (Live Recording, ассистенты генерации сценариев) рассматривается как последующие этапы и не влияет на базовую архитектуру.
